- The repo is split into `frontend/` (Vite React SPA) and `backend/` (NestJS + Socket.IO), each with its own `package.json`. Run npm commands inside the relevant folder.
- Patients (list, profile, edit, treatment packages), Appointments (calendar + dashboard "Today’s schedule") and Settings → Treatments/Concerns use the API via TanStack Query (`src/components/patients/patients-api.ts`, `src/components/settings/catalog-settings.tsx`); the Billing page (`src/components/billing/billing-view.tsx`, `GET /api/billing/overview`) is live too; other screens still render mock data. `src/lib/api.ts` and `src/lib/socket.ts` are the integration points.
- Patients (`POST/PATCH /api/patients`, Patients → Add patient / Edit): `firstName`/`middleName?`/`lastName` build `name` (quick registrations from booking still send just `name`); `dateOfBirth` (not in the future) makes the server derive `age` on every read, otherwise `age` is stored as entered; `gender` Male/Female/Other (Norwood vs Ludwig staging); `address`; `emergencyContact { name, relationship, phone }` — all three required when sent. The add/edit form is `PatientDetailsForm` in `patient-dialogs.tsx`.
- Patient history (`backend/src/history`, sidebar → History (`history-view.tsx`, `GET /api/history`: one summary row per patient — hair grade, safety flags, photo count, consent states) and profile → "Patient history", `components/history/`): `GET /api/patients/:id/history`; `PUT …/history/medical` (allergies / NKDA, conditions, medications with `affectsBleeding`, past surgeries, clearance Not required/Pending/Received) and `PUT …/history/hair` (Norwood or Ludwig grade — checked against the scale — donor quality/density FU per cm²/laxity, past treatments, goals) are clinicians only (`history.update`: Super Admin, Doctor) and replace the whole section. Photos (`POST /api/patients/:id/photos`, multipart `file` + angle + milestone + takenOn) and documents (`POST /api/patients/:id/documents`: Surgery consent / Photo consent (needs `photoUse`) / Medical clearance / Other, `signedAt`, format) are open to every role (`photos.upload`, `documents.upload`); files are served only through `GET /api/photos|documents/:id/file` with the auth header (the frontend turns them into object URLs), deleting is Super Admin-only, and consents are withdrawn with `POST /api/documents/:id/revoke` (kept on record). `FileStore` keeps uploads in memory (20 MB each; type is detected from the file's bytes — JPEG/PNG/WebP, plus PDF for documents) — swap it for disk/S3 when a database is chosen. The Visits tab (`visits-tab.tsx`) lists the patient's completed appointments (`GET /api/appointments?patientId=&status=Completed`, `useCompletedVisits`) with medicines given and prescriptions; the profile's Treatment timeline shows the same completed visits (package ones appear as their package step). The financial tab reuses billing (`GET /api/invoices?patientId=`, `BillingSection`, packages). `SafetyStrip` shows allergies, bleeding-risk medication, infectious conditions and pending clearance on the profile and history.
- Demo history files (`SEED_DEMO_DATA=true`): `backend/assets/demo/` holds 35 illustrated clinical photos and 7 signed-form PDFs plus `manifest.json`, loaded into `FileStore` at startup by `history/demo-files.ts`. Demo patient PT-1079 Amit Joshi has the full FUE journey (pre-op → 1 year, for Before & after); PT-1083 has a pre-op set and signed consents; PT-1084 has PRP progress photos and a withdrawn photo consent. Regenerate with `npm run demo:assets` (needs ImageMagick; deterministic).
- Treatment plans (`backend/src/plans`, Settings → Treatment plans, `GET/POST/PATCH/DELETE /api/treatment-plans`, Nurse can only view) are reusable combinations: steps (treatment, gap before it in days/weeks/months, reminder window ± days, complimentary, optional price/quantity) and repeat blocks (`{ repeat, steps }`). `plan-steps.ts` expands blocks and adds gaps. The frontend editor is `components/plans/plan-editor.tsx` (shared by Settings and the package builder).
- RBAC: roles are `SuperAdmin`, `Doctor`, `Nurse`, `Receptionist` (`backend/src/users/user.entity.ts`). Access is per module and action (`patients.delete`, `appointments.checkIn`…), defined in `backend/src/auth/permissions.ts`: `PERMISSIONS` (the catalogue) and `DEFAULT_ROLE_PERMISSIONS` (each role's access at startup, via `grant({...})`). A Super Admin changes access in Settings → Roles & permissions (`components/settings/roles-settings.tsx`; `GET /api/roles`, `PUT /api/roles/:role/permissions` with the role's full list, needs `team.manageRoles`); it's held in memory like other data, Super Admin is locked to full access, and a `role.updated` socket event makes signed-in clients refetch `/auth/me`. Every route carries `@RequirePermission(module, action)`, enforced by the global `PermissionsGuard`; inside services use `can(user, module, action)` / `assertCan(...)` (403). Login, demo login and `GET /api/auth/me` return `user.permissions`; the frontend never hard-codes roles — it uses `useCan(module, action)` / `<Can>` (`frontend/src/lib/use-permissions.tsx`) or `can(user, …)` (`frontend/src/lib/permissions.ts`, whose module/action names mirror the backend). Sidebar pages without `view` are hidden. The per-feature role notes below describe the defaults.
- Backend data is in-memory (`backend/src/common/in-memory.repository.ts`) until a database is chosen.
- A package is a plan applied to a patient (`POST /api/patients/:id/packages` with `items`, `planId?`, `startDate`); each step is priced from Settings unless the doctor set a price (0 waives it) or marked it complimentary — the old fixed "FUE includes 3 free PRP" now lives in the seeded plan TP-2. Due dates aren't stored: `PackagesService.view` works them out — step 0 on the start date, each later step `gap` after the previous visit's actual procedure day (last day for multi-day surgery); until it happens, its booked day or due date stands in (`estimated`). Any step can be booked from the package (`POST /api/packages/:id/sessions/:index/appointment`; a missed visit is rescheduled in place); a normal booking of the same treatment takes the first open step of that treatment (`appointment.packageStep`). Pending bookings (`GET /api/packages/pending`) lists unbooked/missed surgery steps; `GET /api/packages/due?days=7` (not shown in the UI; kept for future patient reminders) lists each package's next non-surgery step once the previous one is done, from 7 days before its window. A package auto-completes when every step is done; cancelling removes its open visits. Surgery = treatments tagged `surgical` in Settings → Treatments; only surgery is scheduled from a package (Pending bookings / calendar day picker), other plan visits are booked as normal appointments. The UI's only reminder is Pending bookings (surgery). Surgery spans 1–3 days; only one surgery per day (`AppointmentsService.assertTheatreFree`); OPD is never blocked. Surgery is never booked as a normal appointment: `POST /api/appointments` (and changing a visit's type) refuses surgical treatments with 400, and the booking dialog doesn't offer them — create a package first.
- Billing from the calendar: `GET /api/appointments/:id/billing` and `POST /api/appointments/:id/payments` (`backend/src/billing`). Every visit has its own invoice — package visits are billed per step (the step's quantity × the package's unit price; ₹0 / nothing to pay when complimentary or waived); other visits get their own invoice priced from Settings (or a charge entered with the first payment). Invoices track `paid`; statuses Pending → Partially paid → Paid. "Mark completed" opens a chargeable visit's bill as Pending (`BillingService.onAppointmentCompleted`; not for complimentary visits or ones with no price in Settings), so it shows on the Billing page and in the dashboard's collected-vs-billed bar (`revenue.unpaidVisits`); undoing completion drops that bill if nothing was paid. Each appointment carries `billStatus`, mirrored from its invoice via the internal `invoice.changed` event, and completed-but-unpaid visits get a "Payment pending" chip.
- EMI: `PUT/DELETE /api/appointments/:id/billing/emi` splits the current balance into installments (must sum to the balance, dates ascending, first not in the past). Payments made after the plan starts fill installments in due-date order (`installmentViews` in `billing.service.ts`).
- Billing actions exist per appointment (`/api/appointments/:id/...`) and per invoice (`/api/invoices/:id/billing|payments|billing/emi`); the frontend addresses a bill by `BillPath`. Payments carry `receivedAt`; seeded paid invoices have matching seeded payments.
- Appointment status is never edited directly: booking → Scheduled; moving date/time of a Scheduled visit → Rescheduled; `POST/DELETE /api/appointments/:id/check-in` (tick in day lists, only on/after the day; sets the patient's lastVisit) → Checked in; `POST /api/appointments/:id/complete` ("Mark completed", only after check-in) → Completed. Checked-in/completed visits can't be rescheduled. Visits still Scheduled/Rescheduled after their day become Missed (`AppointmentsService.sweepMissed`, on every read and every 10 min); Missed visits stay editable — reschedule (→ Rescheduled) or check in.
- Dashboard cards (`GET /api/dashboard/summary`): Total patients, Revenue this month, PRP sessions, Avg grafts this month (subtitle: this month's completed surgeries and total grafts). Grafts use only `PackageStep.actualGrafts`, the count entered after surgery via `PATCH /api/packages/:id/sessions/:index/grafts` — never the estimate given when the package was created; completed surgeries without it are reported as `awaitingCount`.
- Completed appointments are read-only (PATCH → 400); the details dialog shows them as "Appointment details" with every field disabled, but Receive payment still works.
- Inventory (`backend/src/inventory`, sidebar → Inventory, `components/inventory/`): products the clinic stocks (medicines, shampoos, oils…). The SKU/barcode is the record's `id` — sent as `itemId` on `POST /api/inventory`, unique case-insensitively (409), URL-safe characters only, never editable. Prices are INR with up to 2 decimals. `POST /api/inventory/:id/stock { change }` restocks (+) or records a sale (−) and can't go below 0; Super Admin, Doctor and Receptionist add/edit, Nurse only adjusts stock, only Super Admin deletes. Dropping to the reorder level pushes a "Low stock"/"Out of stock" bell notification. Low stock (≤ reorder level) and expiry (expired / within 90 days) are worked out in the frontend (`inventory-api.ts`). 12 sample products (every type, each with an SVG image in `frontend/public/products/`) are always seeded; `imageUrl` accepts an http(s) URL or a site path like `/products/x.svg`.
- Prescriptions: "Complete visit & prescribe" (`complete-visit-dialog.tsx`) sends `prescription: [{ name, itemId?, dose?, frequency?, durationDays? (absent = ongoing), instructions? }]` — clinic stock or any medicine the patient buys elsewhere — kept on `appointment.prescription` and recorded in the patient's history by `history/prescriptions.service.ts` on `appointment.completed` (prescribed by the visit's doctor; items given from stock carry `dispensed`; undoing completion removes it). Doctors/admins can also prescribe from the history (`POST /api/patients/:id/prescriptions`) and stop one (`POST /api/prescriptions/:id/stop`); `GET /api/patients/:id/prescriptions` lists them with `active`/`endsOn`. Active items come back as `prescribed` on `GET …/history` (Medical tab, safety strip); names matching `BLEEDING_RISK` are flagged `affectsBleeding`. Walk-ins without a patient record keep the prescription on the visit only.
- Consultation assessment: completing a Consultation or Hair analysis (not package visits) shows an Assessment block in `complete-visit-dialog.tsx` — concern (required; saved to the patient via `PATCH /api/patients/:id`) and an optional recommended plan. With a plan, the billing view offers "Create package", which opens Edit patient → package builder pre-filled with that plan (`onCreatePackage` → `editing.planId` → `PackageBuilder initialPlanId`). The package stays optional. Completing a visit needs `appointments.complete` (Super Admin, Doctor).
- Medicines at completion: `POST /api/appointments/:id/complete` takes optional `{ medicines: [{ itemId, quantity }] }` (given from stock). All items are checked (exists, not expired, enough stock) before any stock is taken; they're stored on `appointment.medicines` at the selling price of the day and added to the visit's bill. Revoking completion puts them back in stock, and is refused once the bill has payments.
- Invoices have line items (`Invoice.items`: `service` / `medicine`; older invoices have none and are read as one service line via `InvoicesService.linesOf`). Line amounts keep paise; `Invoice.amount` is their sum rounded to whole rupees (payments are whole rupees). Medicines given after a bill was opened are added to it (on an EMI bill, to the last installment). A visit with no Settings price but with medicines is billed for the medicines, and the visit charge is added with the first payment (`needsCharge`).
- Invoice PDF: `GET /api/invoices/:id/pdf` (`billing/invoice-pdf.service.ts`, pdfkit). Uses `backend/assets` (Inter TTF — pdfkit can't embed WOFF2 and the built-in fonts lack ₹ — and the logo); clinic details come from optional `CLINIC_*` env vars. The billing panel's `InvoiceActions` prints it, downloads it, or sends it: on touch devices through the share sheet with the PDF attached; on desktop it downloads the PDF and opens wa.me / mailto with the message ready (a link can't attach files).
